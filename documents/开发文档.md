## 二、工程配置（P0 已落实）

以下几项已按「2D 非像素 + 核显」调好。这里记录改法与理由，换机或重建工程时照此重配：

### 1. 渲染器：Compatibility（已改）

模板原本是 Forward+：

```ini
config/features=PackedStringArray("4.7", "Forward Plus")
[rendering]
rendering_device/driver.windows="d3d12"
```

Forward+ 是面向高端 3D 的渲染器，对 2D 游戏没有额外收益，但会让启动变慢、导出包变大，在 Arc 140T 核显上还更费电。

**已改用 Compatibility**（GLES3），纯 2D 足够，启动最快，兼容性最好。当前 `[rendering]` 段：

```ini
[rendering]
renderer/rendering_method="gl_compatibility"
renderer/rendering_method.mobile="gl_compatibility"
```

`config/features` 里对应为 `"GL Compatibility"`，`rendering_device/driver.windows="d3d12"` 已删除（Compatibility 不走 RenderingDevice）。

重配方式（换机时）：项目设置 → 渲染 → 渲染器 → 渲染方法，选 `Compatibility`，重启编辑器；直接按上面的 ini 改 `project.godot` 也一样。

> 如果后期要做大量 2D 光照 / 屏幕特效，可以再换回 Mobile，但起步阶段不需要。

### 2. 纹理过滤：保持默认 Linear

风格定为非像素（高清 2D），**不做** Nearest 设置，纹理平滑保持默认即可。后面美术按高分辨率出图，不需要 1x 像素对齐。

> 只有改回像素风时才需要：项目设置 → 渲染 → 纹理 → 默认纹理过滤 → `Nearest`。

### 3. 逻辑分辨率：1280×720（已改）

`stretch/mode="canvas_items"` + `aspect="expand"` 保持不变（画面随窗口缩放，不变形），基准定为 720p：

```ini
[display]
window/size/viewport_width=1280
window/size/viewport_height=720
window/stretch/mode="canvas_items"
window/stretch/aspect="expand"
```

非像素风不需要「1 游戏像素 = N 屏幕像素」的整数缩放，720p 基准在 1080p 显示器上放大 1.5 倍即可。美术按 1280×720 画布设计，UI 元素在 720p 画布上相对偏大，排版时注意留白。

### 4. 版本管理（已完成）

## 三、目录结构

工程根是 `D:\project\魔力符文\magic_runes\`（也是 git 仓库根），开发文档已移入工程内的 `documents/`，随代码一起版本管理。

Godot 小项目推荐**按功能分**，而不是按文件类型分（别让 50 个脚本全堆在 `scripts/` 里）：

```
res://
├── core/                # 全局：单例、事件总线、存档
│   ├── game.gd          # 全局状态（当前层数、卡组、资源）
│   └── save_system.gd
│
├── rune/                # 符文系统（本项目核心）
│   ├── rune_data.gd     # 符文的数据结构（Resource）
│   ├── rune_node.gd     # 单个节点定义
│   ├── rune_executor.gd # 执行器：拓扑排序 + 灵力推流
│   ├── rune_editor.tscn # 编辑器场景
│   ├── rune_editor.gd   # 拖拽、连线、校验
│   └── rune_wire.gd     # 连线的绘制与命中检测
│
├── cards/               # 卡牌
│   ├── card_data.gd     # 卡牌模板（Resource）
│   ├── card_pool.gd     # 卡池、抽卡、随机
│   └── data/            # 具体卡牌 .tres
│
├── battle/              # 战斗
│   ├── battle.tscn
│   ├── battle.gd        # 回合流程
│   ├── enemy.gd         # 敌人基类
│   └── enemies/         # 具体敌人 .tres / .tscn
│
├── ui/                  # 通用 UI 组件
│   ├── card_view.tscn   # 卡牌显示
│   └── theme/
│
├── art/                 # 美术素材
│   ├── cards/
│   ├── nodes/
│   └── fx/
│
└── documents/           # 开发文档（本文件）
```

**新手最容易犯的错**：把所有东西塞进一个 `main.tscn`。符文编辑器一定要单独成场景，因为它会是整个游戏里最复杂的界面。

## 四、核心数据结构

### 4.1 符文节点

```gdscript
# rune/rune_node.gd
class_name RuneNode
extends Resource

enum Type {
    SOURCE,   # 灵力入口：无输入，产出 N 点
    SPLIT,    # 分流：1 进 2 出，各一半
    MERGE,    # 合并：2 进 1 出，相加
    LIMIT,    # 限流：上限 N，超出逸失
    ATTACK,   # 攻击：消耗全部输入，造成等量伤害
    STATUS,   # 状态：消耗输入，挂状态层数
}

@export var id: int = 0
@export var type: Type = Type.SOURCE
@export var position: Vector2 = Vector2.ZERO   # 编辑器里的坐标
@export var param: int = 3                     # 入口产出量 / 限流上限
```

### 4.2 符文

```gdscript
# rune/rune_data.gd
class_name RuneData
extends Resource

@export var nodes: Array[RuneNode] = []
@export var links: Array[Vector2i] = []   # (from_id, to_id)
@export var tab_consumed: int = 0         # 占用的卡牌槽位数
```

用 `Resource` 而不是 `Dictionary` 的好处：可以在 Godot 检查器里直接调、能存成 `.tres`、能做收藏功能（每个收藏的符文就是一个 `.tres` 文件）。

### 4.3 卡牌

```gdscript
# cards/card_data.gd
class_name CardData
extends Resource

@export var id: StringName
@export var display_name: String
@export var node_type: RuneNode.Type
@export var input_cost: int      # 消耗灵力（0 表示是入口）
@export var output_amount: int   # 产出灵力（入口用）
@export var effect_value: int    # 伤害 / 状态层数
@export var description: String
```

一张「火符」就是一份 `.tres`：`node_type = STATUS`，`input_cost = 3`，`effect_value = 3`。

## 五、执行器（最重要的 100 行）

### 5.1 算法

```
输入：RuneData
输出：Result { 总伤害, 各状态层数, 逸失灵力 }

1. 建图：nodes 按 id 索引，links 建邻接表
2. 拓扑排序（Kahn 算法），检测环 → 有环直接报错
3. 按拓扑序推流：
   flow[node] = 0
   对每个 SOURCE：flow[node] += param
   对每个其他节点：
      inflow = flow[node]
      按类型处理：
        SPLIT  → 每个下游 += inflow / 2
        MERGE  → 无操作（下游的输入会自己累加）
        LIMIT  → 下游 += min(inflow, param)，多余记逸失
        ATTACK → 伤害 += inflow；flow 归零
        STATUS → 层数 += inflow；flow 归零
4. 汇总
```

**关键点**：MERGE 不需要特殊处理，它只是「有两条入边」而已——入边的流量在累加时天然相加。这个简化能省掉很多代码。

### 5.2 GDScript 骨架

```gdscript
# rune/rune_executor.gd
class_name RuneExecutor

class Result:
    var damage: int = 0
    var statuses: Dictionary = {}   # StringName -> int
    var wasted: int = 0
    var valid: bool = true
    var error: String = ""

static func execute(rune: RuneData) -> Result:
    var res := Result.new()

    # 1. 邻接表
    var out_edges := {}
    var in_degree := {}
    for n in rune.nodes:
        out_edges[n.id] = []
        in_degree[n.id] = 0
    for link in rune.links:
        var f: int = link.x
        var t: int = link.y
        if not out_edges.has(f) or not in_degree.has(t):
            res.valid = false
            res.error = "连线指向不存在的节点"
            return res
        out_edges[f].append(t)
        in_degree[t] += 1

    # 2. 拓扑排序（Kahn）
    var queue: Array[int] = []
    for id in in_degree:
        if in_degree[id] == 0:
            queue.append(id)
    var order: Array[int] = []
    while not queue.is_empty():
        var cur: int = queue.pop_front()
        order.append(cur)
        for nxt in out_edges[cur]:
            in_degree[nxt] -= 1
            if in_degree[nxt] == 0:
                queue.append(nxt)
    if order.size() != rune.nodes.size():
        res.valid = false
        res.error = "回路里有环，无法执行"
        return res

    # 3. 推流
    var flow := {}
    for id in out_edges:
        flow[id] = 0
    var by_id := {}
    for n in rune.nodes:
        by_id[n.id] = n
        if n.type == RuneNode.Type.SOURCE:
            flow[n.id] += n.param

    for id in order:
        var node: RuneNode = by_id[id]
        var amount: int = flow[id]
        match node.type:
            RuneNode.Type.SOURCE:
                pass
            RuneNode.Type.MERGE:
                pass
            RuneNode.Type.SPLIT:
                var half := amount / 2
                for nxt in out_edges[id]:
                    flow[nxt] += half
                if amount % 2 != 0:
                    res.wasted += 1
            RuneNode.Type.LIMIT:
                var passed := mini(amount, node.param)
                res.wasted += amount - passed
                for nxt in out_edges[id]:
                    flow[nxt] += passed
            RuneNode.Type.ATTACK:
                res.damage += amount
                flow[id] = 0
            RuneNode.Type.STATUS:
                var key := StringName(node.type)  # 实际应从卡牌数据取状态名
                res.statuses[key] = res.statuses.get(key, 0) + amount
                flow[id] = 0

    # 4. 校验：至少一个终结节点
    var has_sink := false
    for n in rune.nodes:
        if n.type == RuneNode.Type.ATTACK or n.type == RuneNode.Type.STATUS:
            has_sink = true
            break
    if not has_sink:
        res.valid = false
        res.error = "没有攻击或状态节点，灵力无处可去"
    return res
```

> 注意：上面 STATUS 那行只是示意，实际状态名应该由 `CardData.id` 决定，不要用节点类型当 key。

## 六、编辑器实现要点

这是整个项目里最花时间的部分。建议分三步做，每步都能看到东西：

### 第 1 步：静态布局（1～2 天）

- 一个 `Control` 当画布
- 节点用 `Panel` 加 `Label` 拼，手动摆在固定位置
- 连线用 `Line2D`，坐标写死

目的：确认视觉比例（节点多大、间距多少、线多粗）在 1280×720 下能不能看清。

### 第 2 步：可拖拽（2～3 天）

- 节点用 `Control` 的 `_gui_input()` 处理拖动
- 拖动时更新 `position`，连线的端点跟着重算（连线要存「从哪个节点的哪个端口出」）
- 用「每帧重画」的方式更新连线：`queue_redraw()` + `_draw()`

### 第 3 步：连线（3～5 天，最麻烦）

- 每个节点四边各留一个端口区域（±8px）
- `_gui_input` 里：按下端口 → 记录起点 → 拖动时画虚线预览 → 松开时判定落点是否是端口
- 合法性：不能自己连自己、不能重复连、不能形成环（保存时用拓扑排序统一校验）
- 断开：点连线 → 删除

**省力技巧**：连线不要用 `Line2D` 成百上千个实例，用单个 `Node2D` 的 `_draw()` 一次性画完所有线，性能好很多，删改也简单。

## 七、开发顺序（每个阶段都要能跑起来）

| 阶段 | 目标 | 验收标准 | 预估 |
| --- | --- | --- | --- |
| P0 | 工程配置 + 目录骨架 | 渲染器/分辨率改好，能导出 exe | 半天 |
| P1 | 执行器 + 单元测试 | 命令行跑通 4 组用例，控制台打印结果 | 2～3 天 |
| P2 | 静态符文场景 | 屏幕上摆出 3 个节点、2 条线，点按钮能显示伤害数字 | 2 天 |

## 八、GDScript 编码约定

- 文件名全小写下划线：`rune_executor.gd`
- 类名大驼峰：`class_name RuneExecutor`
- 变量/函数小写下划线：`var in_degree`、`func execute()`
- 信号用过去式：`signal rune_executed(result)`
- 一个脚本对应一个场景，除了纯数据和纯工具类
- 所有跨系统通信走 `core/game.gd` 或事件总线，不要让战斗场景直接引用编辑器场景
